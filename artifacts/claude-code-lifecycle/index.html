Claude Code Lifecycle

What actually happens between you pressing Enter and the reply landing: where settings, CLAUDE.md, skills, plugins and mods are discovered, when each hook fires, how a tool call clears permissions and the sandbox, and what the model sees at every point. Laid out like the React lifecycle chart: phases top to bottom, every step tagged by who runs it.

You Harness Hook (settings.json) Mod (plugin hooks module) Skill Model

Harness = the Claude Code process itself. Hooks = shell commands from settings.json that run on named events. Mods = your three plugins (context-bar, documented, skill-ledger), JavaScript modules loaded inside the harness that wrap engine events. Boxes marked unverified are inferred from behaviour on this machine, not from the docs.

The four phases

Startup runs once. A turn runs every time you submit. The tool loop runs zero to many times inside a turn. End and housekeeping run when the model stops, when context is compacted, and when the process exits.

PHASE 1

Startup

once, at claude launch or resume
Merge settings
Managed › --settings › .claude/settings.local.json › .claude/settings.json › ~/.claude/settings.json. Arrays like permissions.allow merge; scalars take the highest level. auto and bypassPermissions as defaultMode are ignored from project files.
Load instructions
Managed CLAUDE.md › ~/.claude/CLAUDE.md › every CLAUDE.md from / down to cwd › CLAUDE.local.md. Concatenated, never overridden. @imports up to 4 hops. Subdirectory files load lazily on first read/edit there. Delivered as a user message after the system prompt.
Here: /Users/robby/CLAUDE.md loads for every session under your home.
Load memory
First 200 lines / 25 KB of ~/.claude/projects/<project>/memory/MEMORY.md. Topic files on demand. Not passed to subagents (forks excepted).
Index skills
Scan ~/.claude/skills/*/SKILL.md, .claude/skills/, nested and --add-dir copies, plugin skills/. Only name + description enter context now (combined text capped at 1,536 chars each). Enterprise › personal › project on name clash.
Here: 25+ personal skills from the dotfiles symlink; coach is one line of description until invoked.
Load plugins → mods
For each enabled plugin: skills/, commands/, agents/, hooks/hooks.json, .mcp.json, .lsp.json. A hooks.json with modules: loads JS into the harness; its register(on) subscribes to engine events. /reload-plugins re-reads them.
Here: context-bar, documented, skill-ledger from marketplace mac-dotfiles; swift-lsp, cloudflare from theirs.
Connect MCP servers
Plugin and configured servers connect; claude.ai connectors (Strava, Gmail, Calendar…) attach. Tool names and server instructions enter context; full schemas stay deferred until ToolSearch pulls them.
session.start
Mods see the new session first: register slash commands, read env, cache the session id.
Here: all three register /context-bar, /documented, /skill-ledger.
SessionStart hooks
Input: source = startup | resume | clear | compact | fork. Cannot block. stdout or additionalContext is injected into the first turn.
Here: blocked_notice.sh (the "18 blocked items" banner) and tmux-sn-state clear.
Status line
The statusLine script runs now and after every assistant message, compact, mode change (300 ms debounce). Local only, no tokens.
Here: statusLine: null; the tmux sidebar panel does this job from mod stamps.
Exit → waits for the first prompt. Everything above is already in the model's context window before you type.
PHASE 2

Turn

every time you submit
You press Enter
Prefix decides the kind: /name skill or command · !cmd shell, output lands in the session · @path file mention · plain text.
UserPromptSubmit hooks
Run before the model sees anything. Exit 2 or decision:"block" rejects the prompt with a reason; stdout or additionalContext is appended to it. 30 s timeout.
Here (3): ingest/route_hook.py (bare URL/image → ingest), viz_route_hook.py (structure visual → artifact-diagramming), tmux-sn-state work (sidebar 🔧).
prompt.submit
Mods wrap the same moment with next(e) middleware.
Here: documented clears last turn's 📝 stamp.
Expand a typed /skill
UserPromptExpansion hooks run; SKILL.md renders with $ARGUMENTS (or an appended ARGUMENTS: … line), $1, ${CLAUDE_SKILL_DIR}; each !`cmd` runs now and its output replaces the placeholder. Skill-frontmatter hooks register for the session. allowed-tools are pre-approved for this turn only.
Mod: engine raises skill.prompt → skill-ledger appends a "slash" row.
Assemble the request
System prompt + CLAUDE.md + MEMORY.md + skill descriptions + tool names + the whole transcript so far (older tool outputs may already be cleared) + your prompt + hook context. The whole thing goes to the API.
Model turn
Returns text and/or tool_use blocks. Text streams to you as it arrives (MessageDisplay hook, 10 s). A natural-language ask that matches a skill description makes the model call the Skill tool, which is itself a tool call (Phase 3) whose result is the rendered SKILL.md.
Exit → tool_use present: Phase 3, then back here with results. No tool_use: Phase 4.
PHASE 3

Tool call

zero to many per turn; parallel calls run as a batch
tool.call (outer)
A mod's on("tool.call", {tool}) wraps the whole call: it sees the args before and the result after next(e).
Here: skill-ledger marks a Skill call pending so the inner skill.prompt is recorded as "nl", not "slash".
PreToolUse hooks
Input: tool_name, tool_input, tool_use_id. Can return permissionDecision allow | deny | ask | defer (precedence deny › defer › ask › allow across hooks) or exit 2 to block. Can inject context.
Here: none configured.
Permission rules
deny → ask → allow, first match wins; specificity does not reorder. A hook's allow skips the prompt but deny and ask rules still apply.
Here: ~75 allow rules — db.py:*, metrics.py:*, the Strava and Chrome MCP tools, git commit:*…
Permission mode
auto: a classifier model reviews the call in the background and blocks the risky class (force-push, secrets to public repos…) → PermissionDenied hook, retry:true possible. default/acceptEdits: unmatched calls prompt you → PermissionRequest hook (JSON decision only) → Notification hook permission_prompt. plan: no edits. bypass: no prompts.
Here: a prompt fires notify.sh (phone) and tmux-sn-state blocked (sidebar ⏸).
Sandbox (Bash only)
macOS Seatbelt wraps each Bash command: write allow-list, network through a filtering proxy, Unix sockets limited (Postgres allowed here). File tools, MCP servers and hooks run outside it. dangerouslyDisableSandbox:true is a separate "unsandboxed" prompt; excludedCommands skip it.
Execute
Built-in tool, MCP tool (Elicitation hook if the server asks you something), Skill tool (renders SKILL.md), or Agent tool (SubagentStart → its own Phase 2/3 loop in a fresh context → SubagentStop; only a summary returns).
PostToolUse / PostToolUseFailure
See the result; cannot undo it. stderr and additionalContext go back to the model. Default 600 s.
PostToolBatch
After a parallel batch, before the next model call. Can stop the loop.
Exit → results appended as a user message → Phase 2 "Model turn" again. Mods' tool.call returns here.
PHASE 4

End & housekeeping

when the model stops; on compaction; on exit
Stop hooks
Input: last_assistant_message, stop_hook_active, background_tasks. Exit 2 or decision:"block" forces the model to continue (guard with stop_hook_active or you loop forever). StopFailure instead on an API error.
Here: tmux-sn-state done (sidebar ✅).
session.measure
Fires after a turn whose context fill moved. Mods can read $.session.usage().
Here: context-bar stamps @cc_ctx + @cc_model on the tmux pane; the sidebar draws ctx 7% ███░.
Notification idle_prompt
Claude is waiting on you. Cannot block.
Here: notify.sh → macOS / phone.
Status line + queue
Status line re-runs. Queued messages (typed while it worked) are sent now; Ctrl+Enter sends them earlier.
PreCompact → PostCompact
When context nears the limit, or on /compact. Older tool outputs are cleared first, then the conversation is summarised. PreCompact can block. Project CLAUDE.md is re-read; each invoked skill's latest render is re-attached (5k tokens each, 25k total). SessionStart fires again with source:"compact".
SessionEnd
On exit or /clear. Shared 1.5 s budget (raisable to 60 s). Cannot block.
Headless twin: claude -p
Dispatch jobs run this exact lifecycle without a terminal: same hooks, same mods (isInteractive:false), no prompts (unmatched calls are denied). Needs --setting-sources user,project,local or hooks and skills never load. SessionStart's blocked_notice.sh runs there too.
Exit → idle. Next Enter starts Phase 2 again with the same context (or the compacted one).

The turn loop

The part the four lanes can't show: it is one loop. A turn is model → tools → model until the model answers with no tool call. Mods wrap each tool call from the outside; hooks fire at fixed points inside; the permission gate sits between "the model wants this" and "it ran".

The permission gate

Every tool call clears this in order. The thing people get wrong: rule order is fixed at deny → ask → allow and specificity never reorders it, so an allow rule cannot carve an exception out of a deny. The sandbox is a separate layer that only wraps Bash.

Hook events

Hooks are entries in settings.json (user, project, local, managed), a plugin's hooks/hooks.json, a skill's frontmatter (registered on invocation, kept for the session; the only place once:true is honoured) or a subagent's frontmatter. Types: command (stdin JSON, exit code), http, mcp_tool, prompt (single-turn model eval, 30 s), agent (experimental, 60 s). Every input carries session_id, transcript_path, cwd, permission_mode, hook_event_name.

Mods vs hooks vs skills

Three extension points, three different places in the process. A hook is a subprocess the harness calls at a fixed point. A mod runs inside the harness and wraps engine events as middleware. A skill is text the model reads.

Hook  subprocess at a fixed point

  • Declared in settings.json / hooks.json / skill frontmatter.
  • Gets JSON on stdin, answers with exit code + JSON on stdout.
  • Can block (exit 2) or inject text into the model's context.
  • Runs outside the sandbox. Cannot see the UI or the context meter.
  • Yours: 9 command hooks across 6 events, all shell scripts.

Mod  plugin hooks module, in-process

  • hooks/hooks.json → {"modules":["./x.mjs"]}; the file exports register(on).
  • Subscribes with on("event", {filter}, async ($, e, next) => …) and calls next(e) to let the engine proceed. Wraps, not just observes.
  • Events used here: session.start, prompt.submit, tool.call, skill.prompt, command.run, session.measure.
  • Host API used here: $.command.register, $.session.usage, $.process.run, $.store.get/set, $.ui.toast, $.fs.read, $.env.get.
  • Rule on this machine: mods draw nothing above the prompt; they stamp tmux pane options and the sidebar panel renders them.

Skill  text the model reads

  • SKILL.md with frontmatter: name, description, disable-model-invocation, user-invocable, allowed-tools, model, effort, context: fork, hooks, paths.
  • Only the description is in context at startup. Two ways in: you type /coach … (expansion in Phase 2) or the model calls the Skill tool (Phase 3). Either way the body is injected with ARGUMENTS:.
  • !`cmd` lines run before injection; a failure aborts the invocation.
  • Survives compaction: latest render re-attached, 5k tokens each.
  • Here: skills dir is a read-only symlink; state goes to Postgres via db.py.
